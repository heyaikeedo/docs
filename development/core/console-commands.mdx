```bash
php bin/console list
php bin/console help app:locale:extract
```

The console boots the same application as a web request, so commands see the same configuration, services and plugins. Entity changes are flushed when the command finishes.

<Note>
  Without a database configured, only the three `app:locale:*` commands are registered. Everything else needs a connection.
</Note>

## Application commands

### `app:import:seeds`

Imports the starter templates and categories shipped with the release, from `data/seeds`.

| Option | Purpose |
| --- | --- |
| `--set`, `-s` | Import only the named set; repeatable. Defaults to all. |

Also available as `app:import:presets`. See [Starter content](/advanced/seed-data).

### `app:locale:extract`

Scans sources and updates `.po` catalogs.

| Option | Purpose |
| --- | --- |
| `--target`, `-t` | `core` or a package name; repeatable |
| `--all`, `-a` | The application and every package |
| `--path`, `-p` | Scan an arbitrary directory, such as a theme repository |
| `--locale-dir` | Where `--path` writes catalogs |
| `--domain` | Override the gettext domain |
| `--language`, `-l` | Restrict to specific languages |
| `--no-prune` | Keep entries no longer present in the source |
| `--no-build` | Skip rebuilding the browser catalogs |

### `app:locale:translate`

Fills in missing translations using an AI model.

| Option | Purpose |
| --- | --- |
| `--lang`, `-l` | Languages to translate |
| `--all`, `-a` | Every language with a catalog |
| `--target`, `-t`, `--path`, `-p` | Same targeting as extraction |
| `--force`, `-f` | Retranslate entries that already have a translation |
| `--dry-run` | Show what would change |
| `--no-build` | Skip rebuilding the browser catalogs |

Model and API credentials are read from options and the environment.

### `app:locale:build`

Rebuilds the browser translation catalogs under the web root.

| Option | Purpose |
| --- | --- |
| `--lang`, `-l` | Specific languages |
| `--enabled`, `-e` | Only the enabled ones |

### `app:make:module`

Scaffolds a new core module under `src/`. It asks for the module name interactively and refuses a name that already exists. This is for work on the application itself; plugins don't use it.

### `app:generate-key`

Writes a new `APP_ENCRYPTION_KEY` into `.env`. Stored credentials are encrypted with this key.

| Option | Purpose |
| --- | --- |
| `--force` | Replace a key that is already set, after a confirmation |

New installations get a key from the installer, so this is for installations that predate encryption. Without `--force`, an existing key is left alone.

<Warning>
  Replacing a key that is in use makes every value encrypted with it permanently unreadable, and every connected service has to be set up again. Back the key up together with the database.
</Warning>

### `app:queue:work`

Runs queued background jobs until it is stopped or reaches a limit.

| Option | Default | Purpose |
| --- | --- | --- |
| `--queue` | All queues | Queues to work, comma separated, the first one first |
| `--sleep` | `3` | Seconds to wait when there is nothing to do |
| `--time-limit` | `0` | Seconds after which no new job is started; `0` for none |
| `--memory` | `256` | Megabytes of memory after which the worker exits |
| `--max-jobs` | `0` | Jobs after which the worker exits; `0` for no limit |
| `--stop-when-empty` | Off | Exit as soon as the queues are empty |
| `--cron` | Off | Mark the worker as started by cron rather than kept running. It's listed as a cron worker on the Queue page and counts toward the limit of two cron runs working the queue at once. |
| `--allow-root` | Off | Run as root although the application belongs to another user |

The worker compares its user with the owner of `var/`, which is taken to be the web server's user. As another user it warns. As root it refuses to start unless `--allow-root` is passed, because root-owned cache and upload files can't be changed by the web server afterwards. The worker exits with a non-zero status when its database connection breaks, so the process manager starts a fresh one. See [Background jobs and cron](/development/core/background-jobs-and-cron).

### `app:schedule:run`

Runs the scheduled tasks that are due, without working the queue. `cron.php` does this every minute; the command is for running it by hand. It exits with a non-zero status when a task fails, and `-v` prints each task.

### `app:update`

Unpacks an update archive. It only backs up the files the installation keeps, extracts the release over the installation, and resets OPcache so the next request doesn't run cached copies of the old files. It then starts `app:update:finalize` in a new PHP process, which loads only the new code.

| Argument or option | Purpose |
| --- | --- |
| `file` | Path to the update archive |
| `--unpack-only` | Stop after unpacking, and finish later with `app:update:finalize` |

If the finishing step fails, the files are unpacked but the update isn't finished, and the command says so. Most installations update through the admin panel, which runs the same process. See [How to update](/versioning/how-to-update).

### `app:update:finalize`

Finishes an update whose files are unpacked. It restores the files the update backed up, merging translation catalogs so the release's new strings and the installation's own translations are both kept, then runs database migrations and data migrations, reinstalls plugins, rebuilds translations, copies public files to a custom web root if one is configured, clears the cache, asks workers to restart, and records the new version.

`app:update` runs it for you. Run it by hand to finish an update that stopped halfway. When no update is waiting, it says so and changes nothing. Until an update is finished, `cron.php` does nothing and admin pages redirect to the update page, which finishes it too.

## Doctrine commands

### Migrations

| Command | Purpose |
| --- | --- |
| `migrations:status` | Current state |
| `migrations:migrate` | Apply pending migrations |
| `migrations:list` | List known migrations |
| `migrations:current`, `migrations:latest` | Current and latest versions |
| `migrations:execute` | Run or revert one migration |
| `migrations:generate`, `migrations:diff` | Create a migration, empty or from mapping differences |
| `migrations:dump-schema`, `migrations:rollup` | Squash history |
| `migrations:sync-metadata-storage` | Repair the tracking table |
| `migrations:up-to-date` | Exit code friendly check, useful in deployment scripts |
| `migrations:version` | Mark a migration as applied or not, without running it |

### ORM

| Command | Purpose |
| --- | --- |
| `orm:validate-schema` | Compare mappings with the database |
| `orm:info` | List mapped entities |
| `orm:mapping:describe` | Inspect one entity's mapping |
| `orm:schema-tool:create`, `update`, `drop` | Manipulate the schema directly |
| `orm:generate-proxies` | Regenerate proxy classes |
| `orm:run-dql` | Run a DQL query |
| `orm:clear-cache:metadata`, `query`, `result`, `region:*` | Clear Doctrine caches |

### DBAL

| Command | Purpose |
| --- | --- |
| `dbal:run-sql` | Run raw SQL |

<Warning>
  `orm:schema-tool:update --force` changes the schema without recording a migration, which leaves the migration table out of step. Use migrations on anything but a scratch database.
</Warning>

## Running commands in production

- Run as the web server user, so cache and log files stay writable.
- Redirect output when running from cron; the console writes to standard output.
- Commands exit with a non-zero status on failure, so deployment scripts can check.

## Plugins and commands

Plugins can't register console commands: the command map in `config/commands.php` is static. Expose the action as an admin endpoint, or register a scheduled task instead. See [Background jobs and cron](/development/core/background-jobs-and-cron) and [Data and persistence](/development/plugins/data-and-persistence).
