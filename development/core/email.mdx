Email is sent through Symfony Mailer, with templates rendered by Twig. Which transport is used depends on what an administrator configured.

## Transports

| `option.mail.transport` | Behavior |
| --- | --- |
| `smtp` | Sends over SMTP, using `option.smtp.host`, `port`, `username` and `password` |
| Anything else | A null transport that logs instead of sending |

The null transport is the default, which means a fresh installation silently drops mail until SMTP is configured. That's deliberate: it keeps a half-configured installation from emailing real users.

See [Mailer settings](/email/mailer) and [SMTP](/email/smtp) for the administrator side.

## Sending

```php
use Presentation\Resources\Api\UserResource;
use Shared\Infrastructure\Email\EmailService;
use User\Infrastructure\Emails\WelcomeEmail;

public function __construct(
    private EmailService $email,
    private WelcomeEmail $welcome,
) {}

$this->email->send(
    $this->welcome,
    $user->getEmail()->value,
    [
        'user' => new UserResource($user),
        'locale' => $user->getLanguage()->value,
    ],
);
```

`send(TransactionalEmailInterface $email, string|array $to, array $data = [], array $attachments = [])` sends a [registered email](#transactional-emails). It does nothing while an administrator has the email turned off, and otherwise renders the email's template with your data. The `locale` key picks the recipient's language. Attachments are `Shared\Infrastructure\Email\Attachment` objects:

```php
new Attachment($pdfBytes, 'receipt.pdf', 'application/pdf');
```

`sendTemplate(string|array $to, ?string $template = null, ?array $data = null, ?array $attachments = null)` is the lower-level call underneath. It renders and sends any template, with no on/off switch. Use `send()` for anything an administrator should be able to turn off.

Both merge every option into the template data, so templates can read `option.site.name`, brand settings and policy links without the caller passing them. Both also catch transport errors and log them as "Failed to send email", so a mail failure never breaks the caller, and the caller can't tell it failed.

The sender comes from `option.mail.from.address` and `option.mail.from.name`.

## Templates

Templates live in `resources/emails` and are registered as the `@emails` Twig namespace. Each one extends `layout.twig` and defines a `subject` block and a `content` block.

| Template | Email |
| --- | --- |
| `layout.twig` | The shared shell the others extend |
| `welcome.twig` | Welcome |
| `verify-email.twig` | Email verification |
| `password-reset.twig` | Password reset |
| `workspace-invitation.twig` | Workspace invitation |
| `purchase-confirmation.twig` | Purchase confirmation |
| `invoice-ready.twig` | Invoice ready |
| `export.twig` | Data export |

A translated copy of an `@emails` template can sit in `resources/emails/{locale}`. When the data passed to the email has a matching `locale`, that directory is searched first. See [Email templates](/advanced/email-templates) for more details.

## Transactional emails

Every email the application sends on its own is registered with the service collection under `Shared\Infrastructure\Email\TransactionalEmailInterface`. Registered emails are listed under **Settings → Email → Emails**, grouped by category, each with a **Preview** button and, unless it's always on, an on/off switch.

| Method | Purpose |
| --- | --- |
| `getKey()` | A unique key of lowercase letters, digits and dashes. Prefix a plugin's keys with the plugin name. |
| `getName()` | Translated name shown on the settings page |
| `getDescription()` | Translated one-line description of when the email is sent, and to whom |
| `getCategory()` | One of the `EmailCategory` constants, or a category of your own |
| `getTemplate(?string $locale = null)` | The Twig template, such as `@emails/welcome.twig`. Receives the recipient's language, for emails that ship a translated copy of their own template. |
| `isEnabledByDefault()` | Whether the email is sent before an administrator has saved the settings page |
| `isAlwaysOn()` | Whether the email can't be turned off, because accounts need it to work |
| `getLegacyOption()` | The option path of an on/off switch that existed before the Emails page, read until the page is saved. `null` for new emails. |
| `getPreviewData(UserEntity $admin)` | Sample template data for the preview, shaped like what the sender passes. Nothing is sent. |

`Shared\Infrastructure\Email\AbstractTransactionalEmail` supplies the defaults most emails want: on by default, can be turned off, no legacy option. Extend it and implement the rest.

`EmailCategory` defines the built-in groups, shown in this order: `ACCOUNT` (`account`), `WORKSPACE` (`workspace`), `BILLING` (`billing`) and `ADMIN` (`admin`). Any other category string is listed after them, with a label made from the string.

Switches are saved in the `emails` option, as `emails.<key>.enabled`. `Shared\Infrastructure\Email\EmailSettings` reads them:

| Method | Purpose |
| --- | --- |
| `isEnabled(string\|TransactionalEmailInterface $email)` | Whether the email should be sent. A key nobody registered counts as enabled. |
| `get(string $key)` | The registered email, or `null` |
| `groups()` | Every registered email with its state, grouped by category, for the settings page |

`EmailSettings` reads the database each time rather than the cached options, so a long-running queue worker stops sending an email as soon as it's turned off.

| Key | Name | Category | Always on |
| --- | --- | --- | --- |

## What triggers mail

| Trigger | Email | Sent from |
| --- | --- | --- |
| `UserCreatedEvent` | Welcome, and email verification | Event listeners, in the request |
| `EmailVerifiedEvent` | Welcome | Event listener, in the request |
| `UserEmailUpdatedEvent` | Email verification for the new address | Event listener, in the request |
| `PasswordRecoveryCreatedEvent` | Password reset | Event listener, in the request |
| `InvitationCreatedEvent` | Workspace invitation | Event listener, in the request |
| A paid order is fulfilled, or its invoice is issued or fails | Purchase confirmation | `SendPurchaseConfirmationJob`, a queued job |
| An invoice is issued after the purchase confirmation went out | Invoice ready | `SendPurchaseConfirmationJob`, a queued job |
| An administrator exports users, workspaces, orders or subscriptions | Data export, with the CSV attached | The export request |

Whether the welcome email waits for verification depends on the verification policy. The billing emails run in the background because attaching an invoice means fetching its PDF from the invoicing service. See [Billing](/development/core/billing-subsystem#purchase-confirmation-emails) for when each is sent.

Mail sent from a listener or request handler is sent inside that request, so a slow or unreachable SMTP server slows the request down. Keep timeouts short, and prefer a nearby relay.

## Sending from a plugin

Register your email so administrators can preview it and turn it off. Start with the class:

```php src/DigestEmail.php
<?php

declare(strict_types=1);

namespace Acme\Notes;

use Override;
use Shared\Infrastructure\Email\AbstractTransactionalEmail;
use User\Domain\Entities\UserEntity;

class DigestEmail extends AbstractTransactionalEmail
{
    public const KEY = 'acme-notes-digest';

    #[Override]
    public function getKey(): string
    {
        return self::KEY;
    }

    #[Override]
    public function getName(): string
    {
        return p__('label', 'Weekly notes digest');
    }

    #[Override]
    public function getDescription(): string
    {
        return __('Sent to each user on Monday, listing the notes they changed last week.');
    }

    #[Override]
    public function getCategory(): string
    {
        return 'notes';   // listed after the built-in groups
    }

    #[Override]
    public function getTemplate(?string $locale = null): string
    {
        return '@acme-notes/emails/digest.twig';
    }

    #[Override]
    public function getPreviewData(UserEntity $admin): array
    {
        return [
            'first_name' => $admin->getFirstName()->value,
            'notes' => [
                ['title' => 'Quarterly plan', 'updated' => '3 days ago'],
                ['title' => 'Launch checklist', 'updated' => '5 days ago'],
            ],
        ];
    }
}
```

Register it in your plugin's `boot()`:

```php src/Plugin.php
use Shared\Infrastructure\Collections\ServiceCollectionInterface;
use Shared\Infrastructure\Email\TransactionalEmailInterface;

$this->loader->addPath(__DIR__ . '/../templates', 'acme-notes');

$this->services->add(
    DigestEmail::KEY,
    DigestEmail::class,
    TransactionalEmailInterface::class
);
```

Write the template against the shared layout, so your message matches the rest of the installation's mail:

```twig templates/emails/digest.twig
{% extends "@emails/layout.twig" %}

{% block subject %}
	Your notes this week
{% endblock %}

{% block content %}
	<p>Hi {{ first_name }},</p>

	<ul>
		{% for note in notes %}
			<li>{{ note.title }}, {{ note.updated }}</li>
		{% endfor %}
	</ul>
{% endblock %}
```

Then send it, from a job rather than a request when you send more than one:

```php
$this->email->send(
    $this->digest,
    $user->getEmail()->value,
    [
        'first_name' => $user->getFirstName()->value,
        'notes' => $notes,
        'locale' => $user->getLanguage()->value,
    ],
);
```

Keep the preview data shaped like what you send, so the preview shows what recipients get. A template that fails with the sample data reports its error in the preview instead of failing the page.

<Warning>
  Don't send bulk mail through this path. It's for transactional messages, sent one at a time. Marketing sends belong in a dedicated platform; see [Event-driven integrations](/development/plugins/guides/event-driven-integration).
</Warning>

## Testing

- Point SMTP at a local catcher, such as Mailpit or MailHog, while developing.
- With the null transport, messages are logged rather than sent: check `var/log/app-*.log`.
- Verify the "from" address is one your provider allows, or messages will be rejected or filtered.
